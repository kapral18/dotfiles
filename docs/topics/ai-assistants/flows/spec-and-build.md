# Spec and build

Use `k-spec` to resolve intent and write a compact packet; `k-build` produces an approved packet's artifacts. An existing implementation approval is not another approval gate.

The packet records old/new rules, intended and preserved differences, the impact map (affected consumers and co-edit set), owned scope, side effects, final check commands or judgment criteria, external decisions, and the applicable shared contract. That contract materializes applicable runtime versions, canonical schema/identity/order examples, the compatibility decision, semantic dependencies, immutable input references, and one integration owner before dependent production; file-disjoint targets alone do not establish independence. Unrun criteria are planned, not red/green evidence. Prepare tests with the change; no pre-approval mutation or check-runner ceremony.

Substantial research uses the strong research band; settled implementation uses the implementation band. The root integrates compact returns and retains decisions, not source transcripts. Workers return produced/blocked artifacts without private checks. Finish docs, genuine artifact-producing generation/build intermediates, and formatting before one final Verify stage. Within Verify, order cheap executable prerequisites before dependent expensive checks, reuse prerequisites inside their owning checks, and do not add a preflight stage or duplicate standalone formal build. Execute known commands directly, once per snapshot/input identity, and use strong final judgment where needed. Report failed/blocked criteria faithfully and apply SOP §3.5 for in-scope evidence-backed recovery. Record preserved invariants and immediate consumers, invalidate affected current-snapshot judgments, and revalidate failed and affected criteria after a repair; retain passing executable-check evidence only for unchanged inputs. Do not repeat unchanged checks or launch speculative post-review cleanup or convergence. Commits, pushes, publication, and destructive actions retain their own explicit authority and point-of-action checks.

See [staged workflows](../subagents.md) for context/lifecycle policy and [truth and verification](../system-prompt/truth-and-verification.md) for evidence semantics.
