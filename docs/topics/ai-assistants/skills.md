# Skills

Skills live in `home/exact_dot_agents/exact_skills/exact_k-<name>/` and deploy to `~/.agents/skills/k-<name>/SKILL.md`.
Claude Code, Pi, OMP, Codex, and OpenCode read the same tree. A skill loads when its description matches the request; "manual" skills load only when invoked by name.

Skills hold task mechanics only. They do not delegate work, keep their own lifecycle, or write memory automatically.

## README writing

`k-readme` is model-invoked for README creation, edits, and reviews. `k-code-quality` also loads it when a repository task touches a README.
It applies [ReadmeRoast](https://github.com/princejain756/readmeroast) to an existing local file after drafting, then checks each finding against the project and the requested scope.
Scores are advisory: factual accuracy and useful examples matter more than reaching 100. Curated lists and internal READMEs do not need artificial install or screenshot sections.

The CLI is pinned in the [pnpm package list](../../../home/readonly_dot_default-pnpm-pkgs) and installed through the [pnpm package workflow](../core/packages/pnpm.md).
The skill checks that the file exists before invoking the CLI, preventing an already-missing path from reaching its GitHub mode.
External URLs and heading anchors are outside the CLI's link check. If the binary is unavailable, the skill uses its rubric without claiming a score.

## Anti-slop writing and UI

`k-anti-slop` covers all six [antislop](https://github.com/miqdadbadjuber/anti-slop) domains and adds local guidance for technical documentation, interface copy, data displays, and localization.
Its nine references load by the requested change; a narrow edit does not load every category present in the surrounding artifact.
`k-code-quality`, `k-code-quality-web`, `k-communication`, `k-readme`, and generated-content work in `k-artifact` route matching work to it. It preserves facts, intended voice, and design direction; existing SOP verification and approval rules remain authoritative.
The bundled Python contrast calculator runs locally without an MCP server. See the [inspection, coverage, and adoption decisions](anti-slop.md).

## Review and verification

`k-review` reviews local changes, PRs, PR feedback, and plans inline. Its **verify mode** runs review rounds until one comes back clean:

1. Two fresh reviewers run in parallel using `k-review`'s [Reviewer launch procedure](subagents.md#profiles). The frozen scope covers the whole task change with its map and memory writes; a later §3 step 5 review in the same task covers only the diff against the baseline the last Verify review saved. Their findings are merged.
2. The main session checks each finding against source and fixes the supported ones the change caused or the request covers, low ones too, without asking, and lists one that held at the task start and the request does not cover under `Proposed:`. Before each fix round it steps back to the user's goal, collects the impact of the planned fixes (every consumer and copy of each rule or function they touch, and every trigger earlier rounds raised on it), and checks each fix against all of them; when a fix would add another special case, or the last fixes caused the new findings, it prefers a simpler fix within the request (one that removes text rather than adding a clause): a new approach, or reverting the part that drifted. This adds no stop.
3. A fix loop: one reviewer checks only the fix diff (with the user's request), and the session fixes its supported findings. A wording-only round gets no review. Reviews repeat while a supported medium or higher finding remains; lows are fixed in the same round without another review. A returned cause (the same trigger in the same function or rule, whatever its wording) gets a read-only investigation and a replaced approach or a revert, not another patch; if it returns again, it goes under `Open:` and, like a `Proposed:` finding, no longer continues the loop, which goes on for every other finding.
4. If the full round found a supported medium or higher finding that this task fixes (one listed under `Proposed:` does not count), another full round runs without asking: two fresh reviewers told every finding fixed, rejected, or proposed so far, reporting only new ones; it is narrowed to what the fixes touched and their consumers, and its reviewers are told so. Once a narrowed round finds no new medium or higher finding, a full round covers the whole scope. Fixes cover the whole class of a finding (every copy or recurrence). Rounds aim at about 3 minutes per reviewer and 5 per round; an overrun, or the same kind of finding two rounds in a row, gets a one-line method change, and the report shows the round trend. A clean fix-diff review or a clean narrowed round does not end the loop; a full round on the whole scope with no new medium or higher finding does. No count of rounds stops it, and it never asks whether to continue.
5. The scope is copied as a baseline for a later review in the same task (a file with an unreviewed fix keeps its pre-fix copy, and `.k-review-deleted.txt` lists deleted paths so a later review skips them while they stay absent); `k-cleanup` keeps it and a handoff records its path. Report what remains.

`k-light-review` is the quick inline variant for small, self-authored, low-risk changes.
`k-code-quality` and its children (`-tests`, `-web`, `-react`) set the writing standard, so most slop is avoided before review.
